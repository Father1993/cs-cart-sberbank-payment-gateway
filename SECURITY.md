# Security Policy

## Поддерживаемые версии

Актуальная разработка ведётся по ветке, помеченной как основная в репозитории
(обычно `main`). Используйте последний тег или коммит на этой ветке.

## Как сообщить об уязвимости

**Не создавайте public issue** с описанием эксплойта, логами с реальными кредами
мерчанта, PAN, паролями или полными callback-телами.

Рекомендуется:

1. Написать maintainers приватно (GitHub **Security Advisories** → *Report a vulnerability*
   для репозитория, если включено) **или** по контактам, указанным в профиле автора проекта.
2. Дать минимальный воспроизводимый сценарий без раскрытия production-данных.
3. Указать затронутую версию (коммит / тег) и среду (CS-Cart версия, PHP).

Ожидаемое соглашение об ответственном раскрытии (coordinated disclosure): короткий срок
на исправление patch-релизом до публичного описания.

## Что никогда не прикладывать к отчёту

- Логины и пароли API Сбербанка, терминалы, боевые URL магазина.
- Файлы из `var/logs/as_sberpay_api/`.
- Полные ответы `getOrderStatusExtended` с данными держателей карт с площадки production.
- SSH-ключи, токены CI, `.env`.

## Платежи и PCI DSS

Модуль не должен хранить полные номера карт и **никогда** не должен обрабатывать CVV/CVC.
Реквизиты API передаются только на сторону эквайринга по HTTPS. Перед **production**-запуском
выполните security review и настройки в соответствии с политикой вашей компании и требованиями
PCI DSS (часто применяется SAQ A или иные профили — уточняйте у комплаенс-офицера).

## Уже скомпрометированные секреты

Если реальный пароль API или ключ попал в git, commit message или issue — **считайте их
скомпрометированными**: смените пароль в личном кабинете/по процедуре Сбера и ротируйте
все связанные токены, даже после удаления строки из кода.
